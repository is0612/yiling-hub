# 多角色 AI 养成中枢：产品与技术开发方案 V1.2

- 状态：开发准备与规格定义
- 默认记忆快照周期：8 天，可按角色调整
- 当前优先级：数据契约、管理后台、本地开发与迁移能力
- 注意：本文是开发蓝图，不代表所有功能已经实现。

## 1. 产品定位

建设一个通用的多角色 AI 管理平台，让用户创建和管理 AI 角色，记录角色的对话与活动，周期性生成记忆快照，并在后续互动中检索相关经历。

大肥鱼、龙娘及用户自定义角色都只是角色实例。角色不与某个渠道或具体平台绑定为同一个概念。

## 2. 核心原则

1. **角色与渠道分离**：角色负责设定、记忆和行为；渠道负责接入外部平台、接收/发送消息。
2. **三层记忆分离**：原始消息/事件、周期快照、长期记忆是不同的数据。
3. **周期不是清理期限**：每隔 N 天生成快照，不代表只保留最近 N 天。原始记录的保留期限独立配置。
4. **快照版本化**：重新生成创建新版本；历史版本可追溯。
5. **记忆按需检索**：不要将全部历史记录塞进每次模型上下文。
6. **先单机、后扩展**：先在本地 Docker 环境开发，初期使用 PostgreSQL；不提前引入 GPU、微服务或独立向量数据库。
7. **规范先行**：数据库模型、OpenAPI 契约、Mock 数据与真实 API 保持一致。

## 3. 第一版功能范围

### 3.1 角色管理
- 查看、搜索、新建、编辑、复制、停用角色。
- 管理角色名称、头像、基础人设和模型配置。
- 展示渠道绑定状态、记忆周期、下一次快照时间。

### 3.2 记忆驾驶舱
- 展示角色信息与记忆状态。
- 时间线区分原始消息、重要事件、长期记忆变化和周期快照。
- 支持按来源渠道、时间范围、记忆类型筛选及关键词搜索。
- 展示记忆来源与详情。
- 提供快照、长期记忆和周期设置入口。

### 3.3 周期快照档案
- 展示覆盖时间、生成时间、状态、总结、重要事件、变化与来源。
- 支持查看旧版本、手动生成、重新生成和人工修正。
- 重新生成不得覆盖历史版本。

### 3.4 记忆设置
- 平台默认周期与角色独立周期。
- 默认 8 天，可设置 1–365 天整数。
- 配置时区、启用锚点、自动归档开关和下一次归档时间。
- 原始消息保留期限独立于快照周期。

### 3.5 渠道管理
- 展示平台连接、角色绑定、连接状态和最近错误。
- 首版可使用占位卡片；必须标注未接入状态。
- 真实接入通过独立 Adapter，不污染核心记忆逻辑。

### 3.6 任务监控
- 首版先用明确标注的 Mock 任务验证页面。
- 真实任务状态包含等待、运行、成功、失败、跳过和等待重试。
- 真实重试操作必须在 Worker 实现后才启用。

## 4. 记忆系统

### 4.1 原始消息与事件
保存标准化的对话、平台事件、时间戳和来源标识，用于追溯、快照生成和长期记忆提炼。

### 4.2 周期快照
每个周期生成阶段性总结，包含重要事件、事实与偏好变化、关系、目标/承诺、未解决话题以及与上一份快照的差异。快照尽可能关联来源记录。

### 4.3 长期记忆
保存仍然有价值的事实、偏好、关系、承诺和目标。长期记忆需要支持更新、失效、来源追溯，不能只是无限追加的文本。

### 4.4 生成与失败处理
周期任务必须有持久化状态、幂等键、重试和补处理机制。模型调用成功不等于数据库保存成功。无活动周期可跳过模型调用，但要记录跳过原因并推进计划。

## 5. 周期规则

- 默认从角色记忆启用时间开始计算。
- 采用左闭右开区间 `[period_start, period_end)`，避免边界消息重复。
- 默认间隔 8 天，周期可按角色独立覆盖。
- 修改间隔默认在当前周期结束后生效，不改变已有快照。
- 手动快照不重置自动计划，并记录类型与覆盖区间。
- 每个周期的自动任务需通过唯一标识和数据库约束防止重复。
- 服务停机后必须能识别并补处理错过的周期。
- 数据库统一保存标准化时间戳，按配置时区计算计划时间。

详细规则见 [记忆系统与周期快照规则](memory-system.md)。

## 6. 数据与身份隔离

每个角色至少有一个全局记忆范围。对已识别的用户按需创建私人记忆范围。不同用户的私人记忆不得进入彼此的检索结果。

跨平台身份不可仅凭昵称自动合并。身份合并必须经过验证流程。数据库需使用唯一约束，避免重复创建记忆范围、重复消息和重复任务。

## 7. 技术选型

- 前端与 API：Next.js App Router + TypeScript
- UI：Tailwind CSS + shadcn/ui
- 数据库：PostgreSQL
- ORM/迁移：Prisma
- 本地依赖：Docker Compose
- 后台任务：后续阶段增加独立 Node.js Worker
- 模型服务：统一供应商适配接口，初期调用外部 API
- 语义检索：先用时间、类型、关键词和 PostgreSQL 文本检索；有需要时再评估 pgvector

Web 与 Worker 可共用仓库，但正式后台任务应作为独立进程执行。初期不强制引入 Redis。

## 8. API 契约

Phase 0 建立 OpenAPI 3.0 契约，作为前端 Mock、后端接口和测试的共同依据。接口清单见 [openapi.yaml](openapi.yaml)。更新接口时必须同步更新契约与类型。

## 9. 安全与部署

- 首版可采用单管理员模式，但公开部署前必须完成安全的登录会话与服务端鉴权。
- 浏览器不能接触数据库密码、服务端密钥或内部服务 Token。
- 平台凭据不得明文暴露或写入普通日志。
- 初期使用一台 Linux 云服务器与 Docker Compose；建议先从 2 vCPU、4 GB RAM、40–60 GB SSD 评估，按实际运行指标调整。
- 数据库备份存放在服务器之外，并进行恢复演练。
- 本地开发、备份、恢复与换电脑流程见 [本地开发与数据迁移规范](local-development-and-data-migration.md)。

## 10. 阶段顺序

1. **Phase 0：** 数据模型、API 契约、记忆规则和安全规范。
2. **Phase 1：** 用 Mock 完成后台页面与交互。
3. **Phase 2：** 接入 PostgreSQL、Prisma、基础 API 和单管理员鉴权。
4. **Phase 3：** 周期记忆引擎、Worker、版本化、重试、补处理和自动化测试。
5. **Phase 4：** 记忆检索与模型对话。
6. **Phase 5：** 接入一个真实外部渠道并验证完整消息链路。
7. **Phase 6：** 部署、备份恢复演练、监控和后续扩展。

每一阶段都先确认范围和验收标准；不要一次生成整个系统。

## 11. 成功标准

第一版成功的衡量标准是：角色可管理；数据可持久保存；系统可按可配置周期生成快照；快照有来源和版本；故障后可恢复任务；检索能返回相关记忆；不同用户的私人记忆隔离；本地数据库可以备份并在新环境恢复。
