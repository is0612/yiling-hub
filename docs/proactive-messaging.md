# 主动找话（Proactive Messaging）

让她在没人跟她说话的时候先开口。两条链，各自独立的开关与闸门：

- **私聊**：攒着想说的话，挑一条发 QQ 私信（第 1–10 节）。
- **群聊**：群安静够久了，她起个头（第 11 节）。

两条都**默认关闭**。

这不是「定时群发」：没有「每 3 小时提醒一次」这类配置。能不能开口由两部分决定 ——
她**有没有真正想说的话**，以及**此刻适不适合说**。

相关代码：

```

server/utils/group-initiative-settings.ts  # 群聊那条的设置与闸门（纯函数，见第 11 节）
```

---

## 1. 为什么默认关

主动找话是唯一一条**她先开口**的路径。默认开的话，用户第一次遇到时的第一反应是
「你谁、你怎么突然找我」—— 这个第一印象比功能本身值钱。所以：

- `PROACTIVE_DEFAULTS.enabled = false`，且**不提供「跟随角色创建自动开启」**；
- 开关在「角色 → 模型设置 → 主动找话」，不在全局设置里；
- 没配过就是关的，读取侧不猜用户意图。

---

## 2. 三段式：想 → 判 → 说

```
① 想（补池）  模型读记忆 + 最近对话 → 输出 1-3 条「想说但还没说的事」→ 落库 PENDING
② 判（闸门）  开关 / 收件人 / 额度 / 每日上限 / 安静时段 / 间隔 / 主人在聊 —— 不花 token
③ 说（写+发） 挑一条 → 写一句 ≤30 字的话 → 发 QQ 私信 → 落成一条 ASSISTANT 消息
```

**为什么不能合成一步**：合成后每次 tick 都要「现想现说」，于是必然出现
「刚聊完又凑上来」和「同一句话反复说」。有池子才有「攒着想问的事终于轮到了」
这件事本身 —— 那正是主动找话像人的地方。

**为什么先判后调模型**：反过来的话，「凌晨三点不该发」要花两次模型调用才发现。
判定全是纯函数，一次 tick 的判定成本是零。

`REFILL_THRESHOLD = 2`：池子里少于 2 条才补一次。留余量是为了「挑」真的在挑；
每次只补一条的话，`pickIntent` 永远只有一个候选，打分逻辑等于不存在。

---

## 3. 闸门顺序（`evaluateProactiveGate`）

| 顺序 | 原因码 | 判什么 |
| --- | --- | --- |
| 1 | `disabled` | 总开关 |
| 2 | `daily_max_zero` | `dailyMax = 0`（等于关掉口子） |
| 3 | `no_recipient` | 有没有可投递的 QQ 私聊 |
| 4 | `quota_exceeded` | 当日模型额度 |
| 5 | `daily_limit` | 今天已发 ≥ 上限 |
| 6 | `quiet_hours` | 安静时段（支持跨午夜） |
| 7 | `min_gap` | 距上一条不够久 |
| 8 | `user_active` | 主人刚说过话 |

顺序是刻意的：**配置性问题（1-5）压在时间性问题（6-8）前面**。
否则日志里天天是「没到间隔」，而真实原因是压根没绑 QQ。

`user_active` 单独说一句：主人刚说完话时她不该「主动找」—— 那是接话，
接话由被动回复链路负责。两条链路抢同一个窗口，只会显得她在刷存在感。

---

## 4. 目的池

- 种类：`SHARE / ASK / INVITE / CONFIDE / CURIOUS / FOLLOWUP`。分类不是为了好看，
  是语气和边界不同（索取 ≠ 倾诉）。
- 去重键：`goalDedupeKey(kind, normalizeGoal(goal))`，配合
  `@@unique(characterId, dedupeKey)` + `createMany({ skipDuplicates: true })`。
  归一化会去掉空白和标点，所以「想问问他最近怎么样」和「想问问他 最近怎么样？」
  是同一条。
- 打分：`confidence × 0.5 + urgency × 0.3 + freshness × 0.2`。
  新鲜度只占两成 —— 给它更高权重，池子会退化成「永远说最新那条」。
- 门槛：`minConfidence` 先过滤再打分。凑数的目的给低 confidence 就自然落选。
- 过期：`PENDING` 超过 14 天转 `EXPIRED`。过期只是不再挑中，不删除（页面还能看到她「想过什么」）。

---

## 5. 收件人从哪来

不要求用户手填「主人 QQ」。理由：填一串数字容易错，填错了还发得出去；
而「最近跟谁私聊过」本身就是答案 —— **没人跟她聊过，她也就不该主动开口**。

实现是取该角色最近一次 `externalConversationId` 以 `c:` 开头的 QQ 会话
（`findDeliveryTarget`）。群聊（`g:` 前缀）不算，主动开口只走私聊。

---

## 6. 发出去之后

事务里做三件事：

1. `proactiveIntent` → `SENT`，写入 `content` / `sentAt` / `recipient`；
2. 新增一条 `ASSISTANT` 消息，`metadata = { source: "proactive", intentId, goal }`；
3. 更新会话的 `lastMessageAt`。

第 2 步不能省：用户回一句「你说啥」时，她读上下文要能读到自己刚说过的话。
不落库的话她只能重新编一遍，而且编的和发出去的那句不一样。

---

## 7. 运行方式

```bash
yarn proactive:run   # 60 秒一轮，常驻
```

不用长定时器（比如「三小时后再叫她」）：进程重启、系统时钟跳变都会让它失效。
每轮重新算一次「现在该不该发」永远是对的，而且判定不花钱。

日志只打非 `skipped` 的结果 —— 绝大多数 tick 本来就该是跳过，
把跳过也打出来，真正的失败会被淹掉。

**不作为 Web 进程内的 `setInterval` 跑**（约束第 8 条）：Web 进程多实例、热重载都会导致重复触发。

---

## 8. 页面上的「立即试一次」

`runProactiveTick({ characterId, force: true })`。

`force` 只跳过**时间类**闸门（安静时段 / 间隔 / 主人是否在聊 / 每日上限），
**不跳过**开关、收件人和模型额度。跳掉那三条，这个按钮就等于「绕过所有保护」，
而它只是个调试按钮。

---

## 9. 已知限制

- **一次性只发一条**。攒了三条想说的话，也只在下一个 tick 说一条，其余留在池子里。
  一次连发几条不是「主动找话」，是刷屏。
- **不重试**。模型报错或发送失败只 `attempts += 1`，等下一个 tick 重新挑（可能挑到别的目的）。
  没有退避队列：主动找话失败一次的代价很小，加队列只会让「她三天前想说的话」突然冒出来。
- **不看用户是否已读**。QQ 私信没有可靠的已读回执，所以「她发了三条你都没回」这件事她不知道。
  真正该做的是「连续 N 条无回应就降频」，但那需要定义「回应」，留到后面。
- **安静时段只按东八区**，与 `usageDayKey` 同一口径。跨时区用户会看到偏移。
- **额度用超时静默跳过**，与 QQ 被动回复一致，不给用户弹窗。

## 10. 回归测试

```bash
yarn test:proactive      # 默认值 / 夹取 / 写入校验 / 跨午夜 / 闸门顺序 / 打分 / 解析
yarn test:proactive-db   # 去重约束 / 跨角色去重 / 东八区日界计数 / disabled,no_recipient,force
```

`test-proactive-db` 故意**不测「真发一条」**：那需要能连上的 OneBot。
一旦它依赖本机有没有开 QQ，红两次之后大家就开始忽略这个测试了。

## 11. 群聊：冷场了自己找话题

同一套人设、同一个 tick 进程，但**另一条链**：「这个群安静太久了，她起个头」。

```
① 记录   适配器每收到一条群消息就更新 group_activities（节流 20 秒一次）
② 判     enabled / 每群每天条数 / 额度 / 安静时段 / 冷场时间 / 最短间隔 —— 不花 token
③ 说     读最近 12 条群消息 + 几条长期记忆 → 写一句话 → 发群 → 落 ASSISTANT 消息
```

### 为什么不能沿用私聊那条

- **节奏的单位不同**：私聊是「这个人」，群里是「这个群」。一个群安静两小时、
  另一个群一分钟几十条，共用一个阈值必然有一边是错的。
- **风险不同**：私聊是「我想跟他说」，群里是当众起头。所以默认更保守
  （`enabled = false`、60 分钟、每群每天 3 条），并且提示词里写死三条：
  不 @ 任何人、不寒暄开场（「大家好」是公告腔）、想不出就输出 `-`。
- **素材不同**：私聊靠目的池（攒着「想做但还没做的事」）；群里没有「非说不可的事」，
  只有「接着刚才的话题说一句」或者「抛个轻的」。所以**不用目的池**，直接现想现说。

### 「安静了多久」为什么要落库

群消息平时**不落库**（她没回话的那一轮一条都不存），所以 `conversations.lastMessageAt`
根本不能当活跃时间用 —— 群里正热闹但没人叫她时，它在库里一动不动，
照它判就会在热聊中插一句「你们怎么都不说话」。

`GroupActivity`（`group_activities` 表，绑定 + 群唯一）记四件事：

| 字段 | 含义 |
| --- | --- |
| `lastMessageAt` | 群里最后一条消息（任何人）的收到时刻 |
| `lastSpokeAt` | 她最后一次在这个群说话的时刻 |
| `lastInitiativeAt` | 她最后一次**真的**开了话题（页面展示用） |
| `lastAttemptAt` | 最后一次为这个群花过模型调用（含「判定不说」），闸门的间隔看它 |

冷场时长取 `lastMessageAt` 与 `lastSpokeAt` 里**更近**的那个：她刚回过一句、
之后没人说话，那不该算冷场。

写入是**节流**的（同一个群最多 20 秒落一次库）：热群一分钟几十条，逐条 upsert 是纯浪费，
而冷场判断的精度是分钟级。被节流掉的消息不会丢 —— 内存里的时间一直是最新的，
下一次落库一起写进去。

### 闸门（`evaluateGroupInitiativeGate`）

| 顺序 | 原因码 | 判什么 |
| --- | --- | --- |
| 1 | `disabled` | 总开关 |
| 2 | `daily_max_zero` | `dailyMax = 0` |
| 3 | `mention_only` | 这个群设的是「仅被 @ 时回复」 |
| 4 | `quota_exceeded` | 当日模型额度 |
| 5 | `daily_limit` | **这个群**今天已开过 ≥ 上限 |
| 6 | `quiet_hours` | 安静时段（默认 23:30–07:30） |
| 7 | `not_idle` | 还没安静够 `idleMinutes` |
| 8 | `min_gap` | 离上次**尝试**不足 `minGapMinutes` |
| 9 | `just_attempted` | （角色级）刚在别的群开过口，30 分钟内不追第二个群 |

第 3 条单独说：「仅被 @ 时回复」是这个群的显式意图（绑定级 `groupChatMode`，或
`groupChatModes` 里对这一群的覆盖），她在那种群里连开口的资格都没有。
档位必须走 `groupChatForGroup()` 按群解析，**不许直读 `binding.groupChat`** ——
一条绑定挂好几个群时，直读会把被覆盖成 `mention` 的群当成 `ambient`，
结果就是「明明设了只回 @，她却自己说起话来」。`force`（页面上的「立即试一次」）也绕不过这条。

第 9 条是按角色算的：每群每天 3 条是「按群」的口径，挂了十个群就是一天三十条，
用户看到的是「这条鱼今天到处找人说话」。所以加一层跨群冷却。

### 一次 tick 只花一次模型调用

按安静时长排序，**第一个过闸门的群**才调模型，然后本角色这一轮就结束。
「判定不说」（模型输出 `-`）也算一次尝试（写 `lastAttemptAt`），
于是不会出现「死群每分钟调一次模型、每次都觉得没话说」。

### 「立即试一次」会真发一条

`POST /characters/{id}/proactive/group-try` → `runGroupInitiativeTick({ force: true })`。
`force` 只跳时间类闸门（安静时段 / 冷场 / 间隔 / 每日条数），
开关、`dailyMax = 0`、额度照判 —— 和私聊那个按钮同一套规矩。

### 已知限制

- **不判断「有多少人在看」**。QQ 群没有可靠的在线人数/已读数，所以「说了没人接」她不知道。
  真实缓解手段是每群每天 3 条 + 跨群冷却。
- **进程重启会丢最多 20 秒的活跃度**（节流窗口内还没落库的那部分）。对分钟级的判断无影响。
- **只在她有消息记录的群里开口**（`group_activities` 有行才可能被挑中）。
  从没说过话、也没人说过话的群，她不会凭空出现。
