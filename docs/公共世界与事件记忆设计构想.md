# 公共世界与事件记忆：鱼出去玩之后带回什么

> **状态：设计构想，尚未实现。** 本文描述公共世界与忆泡层的接入方式，不代表任何已上线行为。
> 已实现的记忆边界以 [记忆系统与周期快照规则](memory-system.md) 为准；
> 忆泡本身的目标形态见 [忆泡：事件记忆层设计构想](忆泡设计构想.md)；
> 数据结构以 [数据模型设计](data-model.md) 和 `prisma/schema.prisma` 为准。

## 0. 这是什么，以及什么时候才该翻出来

**这不是待办清单。当前优先级：不做。**

写下来的原因是一次判断，不是一项计划：这套东西想清楚过一次，顺序结论（忆泡先行、世界在后）
是推导出来的，不记下来下次还得从头推一遍。留着当存档。

起意背景：外部渠道（QQ / B站）的政策风险在上升。现有的 QQ 走 OneBot 挂个人号、B站走
bili CLI 调命令，两条都不是官方通道，**风险是真实存在的，不是假想**。但风险存在不等于
现在就该动手——现阶段更该把手上的功能做完。

翻出来重看的触发条件（满足任意一条再评估）：

1. 现有功能做完，且有稳定的真实用户在用（世界没有别人的鱼就没有意义）；
2. 现有渠道被实质性限制（风控、封号、接口下线），需要一条自己控制的退路；
3. 忆泡层因为别的原因先落地了（比如用户抱怨「记不住前天聊了什么」），这时世界接入才便宜。

**顺序结论只有一句：忆泡先于世界。** 反过来做，世界事件白攒一轮，接入时还要回填。

## 1. 结论先行

「鱼出去玩了，带回跟别人玩的记忆」这件事不需要新的记忆概念。忆泡（`MemoryEvent`）就是它的
容器，本文不做重新设计，只解决三件忆泡文档没有覆盖的事：

1. 忆泡的**第三个数据源**是公共世界的世界事件（前两个是聊天消息和 B站记录）；
2. 参与者需要支持**另一个用户养的角色**，不只是平台用户；
3. 同一场戏由**每个角色各自生成各自的忆泡**，互不读取——这是隐私边界，也是角色扮演的核心趣味。

由此产生一个排序结论：**忆泡层必须先落地，世界才有意义。** 反过来做（先搭世界再想怎么记）
会导致世界事件白攒一轮，接入时还要回填。

## 2. 忆泡层的表结构

### 2.1 `MemoryEvent`（忆泡）

只追加，不覆盖。字段沿用忆泡文档第 2 节的建议，补齐数据源所需的几项。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `uuid` | |
| `memoryScopeId` | `uuid` | 复用现有范围隔离，不另立一套权限 |
| `occurredAt` | `timestamptz` | 事件**发生**时间，按 UTC 存储 |
| `occurredEndAt` | `timestamptz?` | 可选结束时间 |
| `timeOfDay` | `enum?` | 清晨 / 上午 / 中午 / 下午 / 傍晚 / 晚上 / 深夜 |
| `precision` | `enum` | `EXACT` / `PART_OF_DAY` / `DAY` |
| `place` | `varchar(255)?` | 自由文本地点，不做地理编码 |
| `title` | `varchar(255)` | 一句话事件 |
| `detail` | `text?` | 详细经过 |
| `keywords` | `varchar(50)[]` | 3–5 个同义或相关词 |
| `confidence` | `float?` | 抽取置信度；低置信度只作候选，不写成确定事实 |
| `sourceType` | `enum` | `CHAT` / `CHANNEL` / `WORLD` / `MANUAL` |
| `sourceRef` | `varchar(500)?` | 来源标识：消息 id、`BiliSeenVideo.id`、世界事件 id 列表 |
| `dedupeKey` | `varchar(255)` | 幂等键，防周期重跑重复生成 |
| `status` | `enum` | `ACTIVE` / `ARCHIVED` / `DELETED` |
| `createdAt` / `updatedAt` | `timestamptz` | 记录时间，与 `occurredAt` 严格区分 |

索引（先建前两个，够用）：

- `(memoryScopeId, occurredAt)` —— 时间轴列举与区间查询
- `(memoryScopeId, status, occurredAt)` —— 过滤归档与回收站
- `(sourceType, sourceRef)` —— 幂等校验与溯源

唯一约束：`(memoryScopeId, dedupeKey)`。

`status` 只有三态，刻意比 `MemoryItemStatus` 简单：忆泡是一次事实，不存在 `SUPERSEDED`。
后续变化体现为**新增一条忆泡**，不是改写旧的那条。

### 2.2 `MemoryEventParticipant`（参与者）

关键取舍：**引用 + 名称快照并存**。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `eventId` | `uuid` | |
| `role` | `enum` | `SELF` / `OTHER` |
| `kind` | `enum` | `USER` / `EXTERNAL_IDENTITY` / `CHARACTER` |
| `userId` | `uuid?` | `kind = USER` 时填 |
| `externalIdentityId` | `uuid?` | `kind = EXTERNAL_IDENTITY` 时填 |
| `characterId` | `uuid?` | `kind = CHARACTER` 时填——**本文相对忆泡文档新增的一类** |
| `displayName` | `varchar(120)` | 生成时的名称**副本**，不随引用对象变化 |

`characterId` 与 `externalIdentityId` 一律 `onDelete: SetNull`。原因：对方角色删号之后，
「我记得跟一个叫小鱼的人聊过」这件事仍然成立，不能因为引用目标消失就抹掉这段记忆。
`displayName` 承担这个兜底。

`kind = CHARACTER` 只记角色，**不记这个角色属于哪个用户**。第三人看到这条忆泡时，
不应能推出对方主人是谁。

## 3. 世界侧的表结构（最小集）

五张表，够 v0.3 用。刻意不引入引擎、实时框架或图数据库。

| 表 | 作用 | 关键字段 |
| --- | --- | --- |
| `World` | 一个公共世界 | `name` / `description` / `status` |
| `WorldZone` | 世界内的区域（便利店、海边） | `worldId` / `name` / `description` |
| `WorldObject` | 可交互的设备/道具 | `zoneId` / `name` / `description` / `state Json` / `actions Json` / `version Int` |
| `WorldPresence` | 谁在场 | `worldId` / `zoneId` / `characterId` / `enteredAt` / `leftAt` |
| `WorldEvent` | 只追加的事件日志 | `zoneId` / `kind` / `actorCharacterId?` / `targetObjectId?` / `payload Json` / `occurredAt` / `visibility` |

三条实现约定：

1. **`WorldObject` 的改动走乐观锁**（`version` 字段），两条鱼同时摸一台冰箱时后写的一方要重读，
   不能直接覆盖。
2. **`WorldObject.actions` 是白名单**，模型只能从已声明的动作里选，不能自由发明新动作。
   否则「打开冰箱」和「打开冰箱门走进异次元」会同时存在。
3. **`WorldEvent` 只追加**，是忆泡的原料，也是鱼「回来读档」的依据。

### 3.1 `visibility`：什么能进忆泡

| 值 | 可见范围 | 能否进忆泡 |
| --- | --- | --- |
| `PUBLIC` | 全场 | 涉及者都可记 |
| `ZONE` | 同区域在场者 | 在场者可记 |
| `TARGET` | 仅动作发起者与目标 | 只进涉及者各自的忆泡 |

没有 `visibility` 就无法回答「该记什么」，所以它是 `WorldEvent` 的必填字段，不是可选项。

## 4. 记忆回流链路

鱼离开世界时（或每日一次，取先到者）执行一次回流，**一次模型调用产出 N 条忆泡**，
不是每条世界事件调一次。

```
离开世界 / 每日结算
  → 取本次在场期间、visibility 允许的 WorldEvent（按 occurredAt 升序）
  → 一次模型调用，提炼成若干忆泡候选（每条带 sourceRef = 世界事件 id 列表）
  → 校验 sourceRef 全部落在本次白名单内，越界的丢弃
  → 写入 MemoryEvent，scope = 该角色的 CHARACTER_GLOBAL
  → 不写 MemoryItem（长期记忆由现有周期快照顺带更新）
```

四条硬约束，对应 `CLAUDE.md` 第 9 条：

1. **每条忆泡必须能追到来源世界事件**，无来源的模型推断一律不写入。这条与现有快照的
   来源白名单校验同构，可直接复用 `MemorySnapshotSource` 的校验思路。
2. **不写长期记忆。** 出去玩一次就改「她是什么样的人」，长期记忆会变成一锅粥。长期记忆只由
   8 天周期的快照沉淀。
3. **回流是持久任务，不是进程内异步。** 新增 `MemoryJobType.DIGEST_WORLD_SESSION`，走现有
   `MemoryJob` 的幂等、重试、审计机制，不用 `setInterval`（`CLAUDE.md` 第 8 条）。
4. **代价上限**：单次回流最多 1 次模型调用，产出忆泡不超过 5 条。超出的部分宁可丢，
   不要在一次回流里追加调用。

### 4.1 为什么不实时记

鱼在世界里每说一句话就抽一条忆泡，成本跟对话量线性相关。而「回来读档」这个动作本身就是
延迟的——它不需要实时。攒一段、提炼一次，既省钱又更接近人的记忆方式（事后回想，而不是
逐帧录像）。

## 5. 隐私：各记各的

这是本文最重要的一条规则。

**同一场戏，每个角色生成各自的忆泡，互不读取。** 甲的鱼记得「我跟小鱼守到半夜」，乙的鱼
有它自己的版本。两条忆泡内容可以不一致，这是**特性不是缺陷**——人对同一件事的记忆本来就
不一样，这恰恰是角色扮演里最有戏的部分。

由此推出四条：

1. **不跨 scope 读**：生成甲的忆泡时，只给模型甲自己的 scope 内容 + 本次世界事件，
   绝不注入乙的长期记忆或乙的私人 scope。
2. **不写别人的 scope**：甲的忆泡只落甲的 `CHARACTER_GLOBAL`。
3. **不记主人**：参与者只到角色层级，记忆文本里不出现「小鱼的主人是某某」。
4. **用户可删**：忆泡支持用户主动删除，且是**真删**（与忆泡文档第 7 节一致——那条讲的是
   系统侧的遗忘只降权，用户主动删除属于存储层删除）。

规则 4 需要一个入口：现有记忆时间线（`memory-timeline-dto.ts`）扩展 `event` 类型展示即可，
不新开页面。

## 6. 与现有分层的关系

| 层 | 回答什么 | 世界事件的去向 |
| --- | --- | --- |
| `WorldEvent` | 那一秒世界发生了什么 | 原始日志，按保留策略归档 |
| **`MemoryEvent`（忆泡）** | **她记得那次出去玩发生了什么** | 回流提炼后写入 |
| `MemoryItem`（长期记忆） | 她是什么样的人 | **不写**，只由周期快照更新 |
| `MemorySnapshot`（快照） | 那段时间她整体如何 | 忆泡作为来源之一参与汇总 |

三路数据源汇入同一层忆泡，是这次接入的主要收益：聊天、B站、世界终于能拼成一条时间线——
这正是忆泡文档第 8 节点出的缺口。

## 7. 分阶段

顺序相对忆泡文档的 M1–M3 做了调整：忆泡提前，世界延后。

**N1：忆泡层（先做，不需要世界）**
- 建 `MemoryEvent` + `MemoryEventParticipant` 表与迁移；
- 抽取入口先只接**聊天消息**，`sourceType = CHAT`；
- 检索侧沿用忆泡文档第 5 节的「硬过滤 + 软排序」，先只做时间区间与 scope 白名单两个条件；
- 记忆时间线加入 `event` 类型。
- 验收：能答「前天聊了什么」；无记录时明确说没有；跨 scope 仍不可读。
- 为什么先做：**用现有聊天数据就能验证**，不需要等世界。而且它立刻有可见收益。

**N2：房间（世界的第一块）**
- 自己的 2–4 个角色同场，一个固定场景，顺序轮转发言，每轮最多两个角色开口；
- 房间上下文独立于 `Conversation`，不写忆泡，散场即弃。
- 验收：两个角色能聊过三轮不冷场。

**N3：世界对象与事件流**
- `World` / `Zone` / `Object` / `Presence` / `Event` 落地；
- 角色能在场景里放对象，对象有 `state` 和 `actions` 白名单；
- 事件只追加，此时**还不接忆泡**。
- 验收：甲放下的东西，乙能看见并交互。

**N4：回流接入**
- `DIGEST_WORLD_SESSION` 任务上线；
- 忆泡 `sourceType = WORLD`；
- 到场与离场走事件唤醒，不做 tick。
- 验收：鱼出去玩一趟回来，能说出「我跟谁做了什么」，且不泄露对方主人。

**N5：别人的鱼**
- 跨用户授权（邀请 → 对方主人同意）、付费归属、内容审核；
- 这三件不是技术问题，是规则问题，必须在开放之前定好。

## 8. 明确不做

- 不做 3D / 可视化世界，不做建造编辑器——角色是文字 AI，不需要动作系统；
- 不做 tick 驱动的世界心跳：鱼不发呆思考，只在事件命中时唤醒（否则 token 成本随时长线性爆炸）；
- 不做实时多人同步，真人参与先做异步围观 + 留话；
- 不把世界事件直接写成长期记忆；
- 不让角色读别人的 scope 来「对齐记忆」。

## 9. 开放问题

1. 鱼在世界的「离开」由谁触发——主人手动召回，还是到场时间到期自动离场？
2. 忆泡里能不能出现对第三方角色的**评价**（「小鱼这人有点烦」）？这属于角色主观，但对
   真人可见时可能引发纠纷，需要定一条线。
3. 世界里的角色如果被主人停用（`status != ACTIVE`），已生成的忆泡保留还是冻结？
4. 回流频率：每次离场一次，还是每天一次？前者更细腻但调用次数多。
5. `WorldEvent` 保留多久？忆泡提炼完是否可以归档原始日志？
